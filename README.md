# CrashAlert

CrashAlert is an Android prototype for automatic motion checks. After saving a rider profile, the app starts a foreground service with an ongoing notification. It listens to the phone's accelerometer and gyroscope even when the app screen is closed. There is **no Start Ride button and no manual SOS button**. The Ride tab only displays live readings; protection does not depend on opening it.

## Run on a phone

Open this repository in Android Studio with JDK 17 and Android SDK 36, then run the `app` configuration on a physical phone with motion sensors. Complete rider setup, grant notification permission so alerts are visible, and grant location permission for speed, heading and coordinates. The monitoring foreground service now also attempts location updates with the screen closed. In Profile → Open app permissions, choose precise location and Allow all the time if available, especially for reboot recovery. Missing permission, disabled location services, system throttling, power policy and reboot restrictions may prevent a fix. Check the persistent notification and Home status; the app cannot guarantee uninterrupted operation.

The five tabs are **Home** (protection and location status), **Ride** (live speed, heading and sensor readings), **Services** (open a map app search for hospitals or police and open the 112 dialer), **Contacts** (save and manage up to three trusted contacts), and **Profile** (edit rider and encrypted Medical ID, view monitoring status, retry a stopped service, and test the detection screen). Rider setup collects name and optional date of birth, blood group, allergies, conditions and medications. There is no phone verification or account signup yet.

## Detection and escalation

An unvalidated motion heuristic may start a 60-second red self-check with an alarm and **I'm OK** cancel action. If unanswered, the app shows a two-minute contact-help prompt, then a repeating two-minute urgent reminder. The foreground notification opens the emergency screen if the app is in the background. The Profile tab offers a safe UI test that never contacts anyone. These prompts do not confirm a crash. An alert is **attempted automatically only if a cloud backend is deployed, the Android build has its configuration, the rider verifies a phone, and 1–3 international-format contacts are saved**. The ordinary CI debug APK has no backend configuration and sends no automatic alerts. Do not rely on this prototype for emergency response.

Contacts and Medical ID are stored on this device; Medical ID is encrypted with Android Keystore. Two separate opt-ins control inclusion in manual drafts and automatic alerts. A configured alert request sends contact names and numbers, rider name, and a recent accuracy-labelled fix to the cloud; it sends Medical ID only if automatic sharing was selected. The backend attempts SMS via Twilio, stores the incident in Firestore, and runs up to five follow-ups every two minutes through a scheduled job. It can continue after the phone goes offline **if the first request reached the server**. Provider acceptance is not SMS delivery confirmation, and cancellation can race with an already queued message. The service retries a failed cloud cancellation while it remains active; process death can prevent that retry. There is no automated call, 112 dispatch, or hospital outreach. The Services tab opens the phone's map app for a user-initiated search; it does not embed Leaflet or claim verified facility distances.

Speed and heading use Android's location fix, not the accelerometer, and are shown as unavailable if location is missing or stale. The service retains its best recent fix in memory, but it is lost on process death and is not a reliable location history. Battery percentage is sampled on app launch. Firebase phone OTP, Twilio, Firestore and optional n8n code require account configuration and end-to-end device testing. Reports, real place listing/Leaflet, automatic voice calls, and robust offline queueing remain unfinished. Keep provider secrets on the server, never in the APK.

## Cloud setup

See [backend/README.md](backend/README.md). The Android build takes four optional Gradle properties: `crashalertFirebaseProjectId`, `crashalertFirebaseAppId`, `crashalertFirebaseApiKey`, and `crashalertApiUrl` (an HTTPS Cloud Run URL). Supply them in your private `~/.gradle/gradle.properties` or trusted build environment. These Firebase Android identifiers are public client configuration; do not put Twilio credentials or service account keys in the app. Phone sign-in additionally requires registering package `com.crashalert.app` and the signing certificate fingerprints with Firebase. The normal CI APK deliberately leaves cloud configuration empty.

## Build and tests

Run `./gradlew :app:assembleDebug :app:testDebugUnitTest` with the Android SDK installed and `node --test backend/validation.test.js`, or use the repository's GitHub Actions workflow. APKs produced by different signing keys can conflict: uninstall the previous debug APK before installing a newly signed one, which deletes local profile and contacts. Do not use a debug APK for a public safety release.

Source is under `app/src/main/java/com/crashalert/app/`: `ui/CrashAlertAppScreen.kt` is the five-tab shell, `ui/RideScreen.kt` contains the rider and Medical ID form, `telemetry/` owns motion and escalation state, `MonitoringService.kt` runs background checks, `contacts/` stores trusted contacts, `profile/` stores encrypted Medical ID, and `location/` handles freshness and device speed/heading.
