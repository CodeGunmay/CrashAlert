# CrashAlert cloud dispatch (requires deployment)

This Node 20 service verifies Firebase **phone-authenticated** ID tokens, stores incidents in Firestore, attempts SMS using Twilio and accepts a scheduled tick every two minutes. It does not call emergency services. A deployment without all required accounts is not a working alert service.

1. Create a Firebase project and register Android package `com.crashalert.app` with the build certificate's SHA fingerprint. Enable Phone sign-in and Firestore. Configure the phone auth safety requirements shown by Firebase. The Android Firebase app ID, API key, and project ID are client identifiers; the server uses Application Default Credentials with Firestore and Firebase Auth permissions.
2. Create a Twilio Messaging sender capable of reaching your test contact numbers. Configure the provider account and any country-specific sender/registration requirements. Do not place the Twilio token in the APK or repository.
3. Deploy `backend/` to a Node 20+ HTTPS host (for example Google Cloud Run), run `npm ci` after generating/committing a lockfile, and set `FIREBASE_PROJECT_ID`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`, and a random long `CRON_SECRET` as private server settings. Set optional `N8N_WEBHOOK_URL` and `N8N_WEBHOOK_SECRET` only if an n8n workflow is configured. The hook receives event ID, attempt number and provider statuses, **not** contacts, location or Medical ID.
4. Schedule `POST https://<host>/v1/jobs/tick` every minute with header `Authorization: Bearer <CRON_SECRET>`. The endpoint scans due incidents, and the server spaces repeat attempts by two minutes. Configure a Firestore TTL policy for `expiresAt` after reviewing your retention needs. Use separate development and production projects.
5. Configure the Android build's four Gradle properties described in the root README and install an APK signed with the fingerprint registered in Firebase. Verify a test phone in Profile and add one to three consenting contacts as E.164 `+countrycode...` numbers. Test with provider sandbox/test credentials first. The Profile UI test intentionally **never** transmits.

`POST /v1/incidents` accepts `{eventId, riderName, contacts, medicalId?, location?}` from a verified Firebase user. `eventId` makes a repeated request idempotent; each user can create at most one incident per 10 minutes. `POST /v1/incidents/:id/cancel` requests cancellation of later attempts. A scheduled job makes at most six rounds (initial plus five) and stops. Provider response statuses such as `queued` are not proof that a recipient received a message. A phone that is offline before its first successful backend request cannot trigger server follow-ups. This prototype has no durable Android offline queue and does not promise delivery, exact timing or uninterrupted service.
